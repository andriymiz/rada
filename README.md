# RADA

Модульна вебсистема для поступової цифровізації робочих процесів ради. Початковий напрям — підготовка до обліку поіменних голосувань; проєкт не є системою електронного документообігу та не замінює АСКОД.

## Поточний стан

Це початкова основа на Laravel 13 і PHP 8.3. Реалізовано захищений вхід, базові довідники та доменні таблиці, приватне завантаження PDF, журналювання завантажень і staging-модель. Для PDF із текстовим шаром реалізовано вилучення питань і збереження розпізнаних голосів у staging; офіційні результати не потрапляють до основних таблиць без явного підтвердження.

Завантаження потребує автентифікованого користувача. Публічної реєстрації та початкового пароля адміністратора немає. Створюйте облікові записи довірених працівників через Artisan-команду, а перед розгортанням налаштуйте HTTPS, резервне копіювання, керування секретами та відповідні права доступу.

## Вимоги

- PHP 8.3 або новіший із розширеннями Laravel, зокрема `mbstring`, `openssl`, `pdo`, `fileinfo`, `tokenizer`, `xml`, `ctype`, `json` і `bcmath`.
- Composer 2.
- SQLite для локального запуску або PostgreSQL/MySQL для спільного середовища.
- Node.js/npm потрібні лише якщо надалі буде додано frontend-збірку; поточний інтерфейс використовує Blade і звичайний CSS.

## Запуск локально

```sh
composer install
cp .env.example .env
php artisan key:generate
touch database/database.sqlite
php artisan migrate --seed
php artisan rada:user:create
php artisan serve
```

Відкрийте адресу, виведену `artisan serve`, і ввійдіть створеним користувачем. Для PostgreSQL або MySQL задайте відповідні `DB_*` параметри в `.env` замість SQLite. Команда створення користувача працює інтерактивно й не має облікових даних за замовчуванням.

Те саме середовище можна запускати через Laravel Sail, якщо Sail встановлено у проєкті/середовищі; Sail не є обов’язковою залежністю цього стартового каркаса. Для production використовуйте вебсервер із document root на `public/`, а не `artisan serve`.

### Міграції та тестування

```sh
php artisan migrate
php artisan db:seed
php artisan test
```

Seeder додає лише нейтральні приклади структурного підрозділу, депутатів, сесії та питання. Він не створює поіменних голосів. У середовищі, де Composer не може отримати пакети, спершу встановіть залежності зі стандартного Packagist/GitHub, потім виконайте команди вище.

## Структура та межі модулів

- `app/Http/Controllers`, `app/Http/Requests`, `app/Models`, `app/Services`: HTTP, валідація, доменні моделі та сервіси.
- `app/Enums`: контрольовані статуси імпорту, документа й результату голосування.
- `app/Console/Commands`: локальні адміністративні операції, зокрема створення користувача.
- `database/migrations`, `database/factories`, `database/seeders`: схема та нейтральні приклади.
- `resources/views`, `routes/web.php`: Blade UI і маршрути.
- `source_documents` та `imports`: оригінальні документи й запуски імпорту.
- `staged_vote_records`: неревізовані результати розпізнавання; вони не є підтвердженими голосами.
- `roll_call_votes`: підтверджені записи з посиланням на депутата та збереженим `original_name`.
- `audit_logs`: події завантаження й подальших критичних змін.

Структурні області — модулі одного Laravel-застосунку, а не окремі сервіси. Автентифіковані користувачі — лише початкова межа доступу; ролі, дозволи та ізоляцію за підрозділами потрібно визначити до реального впровадження.

## PDF та наступний крок

У формі імпорту приймаються PDF до ліміту `PDF_MAX_KILOBYTES` (за замовчуванням 20 MiB). Файл зберігається на приватному диску `storage/app/private`, а SHA-256 не дозволяє повторно зареєструвати той самий вміст. Перед завантаженням користувач вказує номер сесії; PDF із відповідним текстовим форматом після завантаження розбирається у питання та staging-записи поіменних голосувань.

Після отримання дозволеного для використання зразка PDF:

1. Додайте зразок локально в `storage/app/private/samples/` для аналізу; не додавайте його до Git без дозволу на поширення та перевірки персональних даних.
2. Визначте структуру документа, наявність текстового шару, кодування та якість сканів; лише після цього оберіть текстове вилучення або OCR.
3. Реалізуйте ідемпотентне вилучення у `staged_vote_records`, збережіть вихідне значення та посилання на джерело.
4. Перегляньте staging-результат на сторінці імпорту: валідні та помилкові записи розділені, а підтвердження заблоковане за наявності критичних помилок.
5. Натисніть явне підтвердження, щоб транзакційно перенести перевірені записи у `roll_call_votes`; чернетку можна скасувати й видалити.

**Підтверджені записи є офіційними даними системи та готові для подальшого експорту; staging-записи — лише неперевірені пропозиції й не можуть публікуватися як результати голосування.**

### Експорт для порталу відкритих даних

Увійшовши до системи, завантажте окремі UTF-8 CSV-ресурси через посилання на панелі або в навігації:

- `motions.csv` — перелік порядків денних питань засідань і кількість підтверджених голосів за кожним результатом; `motion_id` ідентифікує питання, `session_id` — засідання.
- `votings.csv` — записи індивідуальних підтверджених голосів, пов’язані з питанням через `motion_id`.

До обох ресурсів включаються лише підтверджені голоси; неперевірені staging-записи не експортуються.

## Альтернативи та компроміси

До розробки варто порівняти цю систему з налаштуванням наявного ПЗ для документообігу/реєстрів, керованою базою даних із формами, або окремим вузьким застосунком для голосувань. Наявні рішення зазвичай швидше впровадити й дешевше підтримувати, але вони можуть не мати потрібної моделі перевірки PDF, локальних правил доступу чи інтеграцій. Власна модульна система краще пристосовується до процесів ради й дає контроль над даними, проте потребує постійної розробки, аудиту безпеки, резервного копіювання, супроводу та відповідальних власників процесів. Перед вибором слід оцінити чинні ліцензії, хостинг, вимоги до захисту даних і доступність інтеграцій.
